## Page purpose and structure

Organize by what the reader wants to do, rather than mirroring rule files. Each page has one reader goal and one type: tutorial (a beginner lesson leading to a first success), how-to (one practical task or closely related tasks), reference (lookup tables), or explanation (an idea necessary to understand a feature). Most pages are how-to pages. Use a verb in a task title. Do not mix a long implementation explanation into task instructions.

After the single level-one title, put exactly:

<!-- generated by docs:update_by_ai -->
<!-- page type: how-to -->

Use the actual page type in the second comment. Under each level-two heading except Related pages, add one or more exact existing repository-relative source comments, such as <!-- source: packages/apps/web_frontend/src/components/CommandPalette.vue -->. Include code sources for code-only facts. These comments are traceability, not visible prose. Use snake_case filenames, valid Markdown and no raw angle-bracket placeholders outside code. Keep paragraphs on single lines without tab indentation.

Start with one sentence describing what the reader can do or find. Explain unfamiliar terms briefly using current glossary names. State the prerequisites, where to find the first control, ordered actions and the observable outcome. Explicitly include required preparation, closing an obstructing window, release of a held control, focus, selection and how to recover when those details matter. Separate alternative opening methods with “or”; do not accidentally turn alternatives into consecutive actions. Distinguish tooltip text, visible labels, folder names, display names and history-entry labels. Do not infer rendered labels directly from backend identifiers.

Use ordinary numbered lists with one action per step. Do not put individual steps in cards or borders. Put exact control names in bold. Use consistent task labels in sidebar and related links. Link to existing next tasks rather than repeating their instructions. Keep paragraphs to three sentences or fewer, and omit internal APIs, source paths, state keys and technical detail that does not help the person use Heidrun Code. A supported timing detail such as “about half a second” belongs only where current sources establish the timing. Reset means the implemented default, not necessarily undoing the user's last custom value.

Use tables for controls, options and meanings that readers look up. Add Related pages with useful task labels and short explanations. Include only supported defaults, limits, remedies and failure conditions.

## Troubleshooting

Use ## Troubleshooting when sources show a likely problem. Give each independent problem its own ### heading, **Cause**, **Solution** as numbered actions and **Check** stating the observable recovery. The reusable theme renders each topic as a separate panel; keep ordinary Markdown, without bespoke HTML or inline CSS. Do not invent symptoms. Distinguish blank input, cancel before saving, save when focus leaves a field, and changing an already saved value. Do not describe an outside click as cancellation when the source saves on blur. A disabled-control recovery should say explicitly which previously disabled control becomes available.

## Authentic screenshots and annotations

Use only verified authentic captures supplied through this run's evidence directory, or existing documented captures that match the current feature and source version. Read the manifest and disclose stale or missing evidence. With no suitable capture, generate useful text without placeholders, invented image paths, generated artwork or claims of visual verification. Do not open applications or acquire new screenshots during this command.

Choose a crop showing the relevant control plus enough surrounding interface for a beginner to locate the region: window edge, top bar, tabs or nearby sidebar. Leave breathing room around the target and omit large empty areas. If necessary, pair an overview with a close-up. Keep UI proportions unchanged and targets/labels legible at roughly600px article width. Do not stretch the screenshot.

Derived SVGs may embed byte-identical original JPEG/PNG data and crop it through a viewport. Keep source-pixel and display coordinates distinct; a clipPath defined in outer display coordinates must not be applied inside a source-pixel viewBox. Record original path, SHA-256, source dimensions, crop rectangle and annotation meanings in adjacent provenance.json. Keep every original capture intact.

Use pure gray #808080 at25% fill opacity for the matte only. Screenshot content, labels, arrows and outlines remain fully opaque. Use dark text with a broad pale outline and soft white glow; use restrained muted-blue target outlines and arrows with dark outlines and a soft pale glow. Draw an arrow as one continuous silhouette so a rounded shaft end cannot protrude through the arrowhead. Put concise labels outside controls without obscuring interface text. Keep one clear purpose per figure. Alternative text must describe the actual captured state, not an imagined result. These are generation rules; theme/image inspection is left to the human review, not an automatic extra pass.
